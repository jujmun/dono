## How to read this document

It has two halves, for two readers.

**Part A is for legal.** It is narrative, clause-first, and frames each problem as exposure: what the document promises, what the product actually does, and what the gap means if the document is published as it stands. Read Part A and the publication gate in Part E.

**Part B is for engineering.** It is a status table over the 46 obligations in `TASKS_engineering_features.md`, each independently re-verified against the current code, with file and line evidence. Read Part B and the Category C findings.

Both halves use the same finding IDs, so a conversation that starts in one can be continued in the other.

## Method, and what would make this document wrong

The repository was cloned at the commit above and read directly — `convex/` (115 files), `app/` (26), `components/` (69), `lib/` (49) — rather than inferred from documentation. Every finding below cites a file, and every high-severity finding cites a line.

Three deliberate constraints:

1. **The clause text is the source of truth, not a paraphrase of it.** Where this document quotes a clause, the quotation is from `dono-brain/terms_v2.2/`, not from the change log or the task lists.
2. **The repository's own copy of `dono-brain/` was diffed against the mounted working copy and is byte-identical.** There is no version skew between the legal documents in the repo and the ones being audited. This was checked first because a mismatch would have invalidated everything else.
3. **Absence was verified by search, not assumed.** Where this document says a control does not exist, the search terms used are recorded in Part B so the claim can be falsified.

**What this document does not cover.** No Stripe sandbox or live-account behaviour was observed; findings about Stripe are inferences from the API calls the code makes, not from what Stripe actually did. The PostHog project's own default settings were not inspected (Cookie Notice 3.2 asks for exactly that check, and it remains outstanding). No clean-browser cookie audit was performed. Test files were read for evidence of intent but a passing test was not treated as proof that a control is reachable from the UI.

## A.2 A1 — The community-fund path defeats the payment-services perimeter argument

This is the most serious finding in the document, and it is serious for a reason that is not obvious from the size of the feature.

ToS 4.2 states:

> **Dono does not receive, hold, safeguard or control donation funds.** … Dono does not operate any pooled fund, community fund, escrow or platform-held balance, and will not do so unless and until it holds any authorisation required for that activity.

ToS 8.4 lists among prohibited categories: "**pooled funds, community funds, or any arrangement under which Dono would receive or hold the money**".

The code does exactly what both clauses prohibit. `convex/stripe.ts:360` creates the payment intent for a community-fund donation with **no `stripeAccount` option** — meaning the charge is created on Dono's own platform account rather than on a connected account. The code says so itself, in a comment at `convex/stripe.ts:355–356`:

> `// Community funds are Merchant of Record on the platform account (not Connect).`
> `// Fee envelope (5% + 20p) is retained on allocation; Stripe fees hit the platform balance.`

and stamps the payment intent with `merchantOfRecord: "platform"` in its metadata (`convex/stripe.ts:373` — every other charge path in the file is stamped `"connected_account"`, at `:272` and `:730`). The money then never moves to any campaign: `convex/stripeFunds.ts:86–131` (`allocateFundDonation`) distributes the donation across eligible campaigns by **incrementing counters** — `ctx.db.patch(campaign._id, { raised, donors, status })` and a `fundAllocations` row. No transfer, no payout, no connected account. The funds sit on Dono's Stripe balance while the campaign pages display them as raised.

The feature is fully wired: five placeholder funds are seeded (`convex/funds.ts:7–13`), the `communityFunds` table is in the schema (`convex/schema.ts:220`), and `createFundPaymentIntent` is an exported public `action` (`convex/stripe.ts:311`) callable from the client.

**Why this is the worst finding rather than merely a bad one.** ToS 4.2 carries a `[SOLICITOR SIGN-OFF — written UK payment-services perimeter memorandum based on the executed Stripe agreement and the live API flow]` marker. That memorandum's conclusion depends on the sentence "Dono does not receive, hold, safeguard or control donation funds." A solicitor asked to write that memorandum against **the live API flow**, as the marker requires, will find a code path in which Dono is the merchant of record, holds the money on its own balance, and decides how it is allocated. The perimeter argument does not survive contact with that path — and the Financial Crime & Payments Policy clause 3 rests on the same foundation.

Two of the seeded placeholder fund slugs also sit inside ToS 8.4's prohibited list on their own terms: `student-hardship` (personal hardship) and `medical-textbooks` (arguably ordinary study costs, and adjacent to the medical-expenses prohibition). This is seed data rather than production content, but it is seed data that ships in the repository.

**Remedy.** Build item 3 in `TASKS_engineering_features.md` is correct and is P0: remove the charge path. Removing the UI while leaving `createFundPaymentIntent` exported is not sufficient — it is a public action, and the clause is about capability, not about whether the button is currently rendered.

## A.3 A2 — Users are not accepting v2.2. They are accepting a stub from before v2.1

The application renders its legal documents from `lib/legal/content.ts` — a hand-written summary, not the v2.2 markdown. `app/legal/[doc].tsx:11,39` reads `getLegalDocumentBody(docId)` from that file and displays it under the version string from `convex/lib/legalDocuments.ts:23–32`, which reads:

```
terms_of_service:        "2026-07-20-v0.1"
society_campaign_terms:  "2026-07-20-v0.1"
student_campaign_terms:  "2026-07-20-v0.1"
donor_terms:             "2026-07-20-v0.1"
community_guidelines:    "2026-07-20-v0.1"
privacy:                 "2026-07-31-v0.2-stub"
cookie:                  "2026-07-31-v0.2-stub"
refund_dispute:          "2026-07-20-v0.1-stub"
verification:            "2026-07-31-v0.2-stub"
```

`convex/lib/legalAcceptance.ts:21–29` writes exactly this string into every `legalAcceptances` row. **Every acceptance record in the database therefore evidences acceptance of a v0.1 stub.** Not of v2.2, and not of anything a solicitor has seen.

The stub is not a neutral summary. It contradicts v2.2 on the substance of at least seven settled decisions:

| Stub text (`lib/legal/content.ts`) | v2.2 position |
|:-----------------------------------------|:-------------------------------------------|
| "By creating an account, **browsing** or using the Platform … you agree to these Terms" (line 14) | ToS 1.3: "Merely browsing a publicly accessible page does not, by itself, make you a party to these Terms." |
| "You must be at least 18 years old to create an account, create a Campaign or **make a Donation**" (line 16) | ToS 1.8 / Donor 2.1: anyone may donate, at any age. This is decision 3 — the single most-revised position in v2.2. |
| "**Campaigns on Dono are Society Campaigns only**" (line 20) | v2.2 has a complete individual Student Campaign regime (document 02, ToS 4.5, 7.4). |
| "paid to the Connected Account of the **Campaign Owner** (Merchant of Record)" (line 18) | ToS 3.1: the Recipient "may be a different person from the Campaign Owner". |
| "Refunds are **recovered from** the Connected Account" (lines 28, 122) | ToS 15.4: the Recipient executes the refund; "Dono does not initiate a refund of a Donation and holds no reserve power to do so." |
| "you may cover Dono's fee and **estimated Payment Provider fees**" (line 30) | ToS 16.1 / Donor 6.1: Payment Provider's applicable fee plus 3.5 percentage points. |
| Contact: `dono.outreach@gmail.com` (lines 5, 12, 80, 88) | Decision 9: one address, `joindono.team@gmail.com`, everywhere. Verified consistent across all v2.2 documents — but not in the product. |

The stub also points readers to `dono-brain/terms/…` — the superseded v1 folder — as the "full draft source" (lines 36, 48, 58, 72, 82, 142).

**Why this compounds every other finding.** Part B catalogues clauses that describe controls Dono has not built. Those clauses are unpublished, so nobody has relied on them. This finding is the opposite: text *is* live, users *are* accepting it, and it is wrong in the user's favour on some points and against it on others. It also means the acceptance-record findings (build items 23–25) understate the problem — an immutable archive of superseded versions is worth little when the version string points at a stub whose content was never the contract.

**Remedy.** This is a prerequisite to publishing anything. Either render the v2.2 markdown directly, or maintain a summary that is generated from it and version-stamped `2.2`. Re-acceptance will be required from every existing user, because the documents they accepted are not the documents Dono intends to rely on.

## A.4 A3 — Checkout promises anonymity the Terms expressly cannot guarantee

Decision 8 in the v2.2 change log is unambiguous: "**'Hide my name' means hidden from the public.** Transaction details may reveal the name; Dono cannot guarantee it is hidden from the Stripe account holder."

ToS 11.3 implements it at length:

> **This setting hides your name on Dono's public pages. It does not hide information the Payment Provider makes available to the Recipient** … the person or Society that operates that account can see the transaction details the Payment Provider shows them, which may include your name. **Dono cannot guarantee that your name is hidden from the holder of the Connected Account.**

The checkout says the opposite. `components/donate-sheet.web.tsx:401–403`:

> "Hide my name (your amount still shows publicly; your name is hidden **from the public and from the campaign owner**)"

The same wording appears in `components/donate-sheet.native.tsx:375–376`.

The backend behaviour is not the problem — `convex/lib/societyDonationLedger.ts:73` does correctly withhold donor identity from the campaign owner's Dono-side view. The problem is that the campaign owner is also a Stripe connected-account holder who can read the charge in their own Stripe dashboard, which is precisely the leak ToS 11.3 was rewritten to disclose. The interface makes an unqualified promise about a channel Dono does not control.

ToS 11.3 additionally requires that "the re-identification risk is explained at the point of selection". No such explanation appears at the point of selection.

**Why this is Critical rather than High.** It is a specific, unqualified factual promise, made at the moment of decision, to a consumer, about a privacy outcome — and it is the one promise the drafting team spent a decision cycle deciding they could not make. A donor who hides their name for a reason that matters to them, and is then contacted by a campaign owner who read the name off a Stripe payout, has a clean complaint.

**Remedy.** Replace with ToS 11.3's own framing, and add the re-identification explanation at the point of selection. This is a copy change plus one disclosure — the cheapest fix among the critical findings, and it should not wait for a release cycle.

## A.5 A4 and A5 — The donation age position is wrong in both directions at once

Decision 3: "**18+ to create an account** (and therefore to create a campaign or comment); **browsing and donating open to everyone.** Age is declared, not verified. Checkout prompt only — no guest donation cap." This is stated identically in ToS 1.8, ToS 11.4, Donor 2.2, Verification 4.3, Privacy 14.2, the Children's Risk Assessment, Illegal-Content RA 2A and OSA Procedures 3.3. The consistency across the documents is exemplary. The product implements neither half.

**[UPDATE — 6 Aug 2026:** Decision 3 has been revised rather than closed by building the missing gates. Account creation and commenting will not get an age gate; the parental-permission checkout alternative will not be built either. All documents listed above have been corrected to state no age gate on account creation/commenting and a flat 18+-only checkout confirmation. See TRUTH.md, Age section, for the current settled position. **A5 below (parental-permission wording) is resolved by this — the wording is now removed rather than built.** A4 (the `donate-dob-gate.tsx` / `ageAttested` discrepancy) is untouched and remains open — it was not part of this decision.]

**A4 — the gate that should not exist.** `components/donate-dob-gate.tsx` requires a signed-in donor to have a stored date of birth showing 18+ before payment can start, and refuses with "You must be at least 18 years old to donate." (`:43`). `components/donate-sheet.web.tsx:414` renders it and `:457` blocks the pay button behind it ("Confirm your date of birth above to continue to payment."). The file's own docstring (lines 19–21) states the design: "For signed-in donors: require a stored adult DOB before payment can start. Guests are handled via the legal checkbox attestation only."

So a signed-in 17-year-old cannot donate, though four documents say they may. This is the *less* dangerous direction — the product is stricter than the promise — but it still means the Terms misdescribe the product, and it means the Children's Risk Assessment and the Privacy Notice's clause 14.2 analysis (which is built on the premise that Dono knowingly processes data about under-18 donors) do not describe the live system.

**A5 — the confirmation that should exist and does not.** ToS 11.4 requires checkout to ask the donor to confirm "**you are 18 or over, or that you have the permission of a parent or guardian to make the donation**". Build item 8 requires it to be actively confirmed on every donation including guest donations, with the wording and version stored.

There is a gate, and it is worse than having none, for three compounding reasons.

**The server enforces the wrong rule.** `convex/stripe.ts:203–208` rejects a donation when `ageAttested` is falsy, with the message "You must confirm you are at least 18 years old to donate." — a flat 18+ statement with no guardian alternative, which is not what ToS 11.4 or Donor 2.2 say. `convex/legalInternal.ts:14–19` repeats the same message.

**The client makes that gate unreachable.** `components/donate-sheet.web.tsx:270` (and `donate-sheet.native.tsx:251`) sends `ageAttested: true` as a **hard-coded literal** on every donate call. It is not derived from any user action — there is no checkbox, and the guardian-permission wording appears nowhere in the codebase. The server check therefore cannot fire from the real interface.

**The stored value evidences nothing.** `convex/stripe.ts:213` and `:248` re-stamp `ageAttested: true` regardless of the argument, so `donations.ageAttested` (`convex/schema.ts:359`) is `true` on every row by construction. `profiles.ageAttestedAt` (`convex/schema.ts:26`) is not populated from anything a donor did at checkout.

So the audit trail records a confirmation that was never sought, in the words of a rule the Terms do not state.

The Children's Risk Assessment §8 item 1 describes this confirmation as "the only control at the point where a child parts with money". At present that control is a constant.

**Remedy.** These are one piece of work, not two: remove `DonateDobGate` from the donation path, add the ToS 11.4 confirmation as an active unticked control for all donors including guests, and store the wording and version. Build item 8.

## A.6 A6 — Dono still initiates refunds on connected accounts

Decision 1: "**Dono cannot and should not initiate refunds.** … engineering must disable the admin refund path." Six documents now state this as fact — ToS 15.4, Refund 1.2 and 6.1, Donor 12.1, Student 9.2, Society 4.2 — three of them in the strong form "holds no reserve power to do so."

The main donation refund path was correctly rebuilt: `convex/refunds.ts:262` (`adminDecide`) creates a `refund_owner_action_required` notification (`:319`) and emails the owner rather than calling Stripe, and the old `processApprovedRefund` is gone. That work holds up.

But `convex/stripe.ts:860` still calls `stripe.refunds.create(...)` **with `stripeAccount` set to the connected account** (`:852–855`). It sits inside `refundAndCancelSocietySubscriptionForNoCampaigns` (`:831`) — a safety net that fires when a society subscription invoice is charged but the society has no active campaigns, refunding the charge in full and cancelling the subscription.

The intent is benign and the donor outcome is good. The problem is that ToS 3.1 defines "Donation" as including "each charge under a Recurring Donation", and a society subscription charge is such a charge. So the clause "Dono does not initiate a refund of a Donation and holds no reserve power to do so" is false as written, and the phrase "holds no reserve power" is exactly the kind of absolute statement that one counter-example defeats. The `[ENGINEERING — BUILD REQUIRED]` marker at ToS 15.4 correctly says an administrative refund path "currently exists in the backend" — but it is pointed at the deleted `processApprovedRefund`, not at this one, so the marker reads as more resolved than it is.

**Remedy.** Either remove the automatic refund and handle the no-active-campaigns case by cancelling the subscription and notifying the society to refund, or narrow the clause to carve out "a charge Dono has taken in error on its own initiative" — a carve-out a solicitor should draft, because it partially reopens the reserve-power question the clause exists to close.

## A.7 A11 — The over-funding rule has no mechanism

Decision 15 turns on a factual premise: "**No de minimis on over-funding (which cannot occur)**". Four documents rely on it — ToS 14.6, Student 5.1, Donor 10.3, Refund 10.3 — and ToS 14.6 puts the premise first: "A Campaign cannot be funded beyond its target, **so over-funding does not arise**."

Nothing enforces it. `convex/lib/applyDonationToCampaign.ts:17–29` is the whole of the arithmetic:

```ts
const raised = campaign.raised + amount;
const status = raised >= campaign.goal ? "funded" : …
```

The status flips to `funded` once the target is reached; the amount is not capped, and `convex/stripe.ts` performs no goal check before creating a payment intent (searched: no reference to `goal` in that file). Two donors confirming concurrently against a nearly-funded campaign will both succeed.

The exposure is the shape of the drafting. Because the clause says over-funding *cannot occur*, it does not describe what happens when it does — and the "every penny refunded, no de minimis" rule that would otherwise cover it is expressly disapplied on the ground that the situation does not arise. So an over-funded campaign falls into a gap the documents deliberately left empty.

**Remedy.** Build item 4 — a hard server-side cap that holds under concurrent donations. Until then, ToS 14.6 and its three siblings should not be published, because they assert as fact something the product does not enforce.

## A.8 What is genuinely in good shape

It would misrepresent the audit to list only failures. Five things were checked and are sound.

**The v2.2 documents are internally consistent on every one of the sixteen decisions.** This was the specific failure mode of v2.1 and it has not recurred. The complaints address appears as `joindono.team@gmail.com` in all ten documents that carry one, with no stragglers. The age position is stated identically in eight places. The "Dono does not initiate refunds" formulation is materially identical across six documents. The fee tables in ToS 16.2 and Donor 6.1 are identical and arithmetically correct (1.5+3.5=5, 2.8+3.5=6.3, 2.5+3.5=6, 3.15+3.5=6.65). Part D records the only two drafting tensions found, both minor.

**The `[ENGINEERING — BUILD REQUIRED]` markers are honest.** Thirty markers across the nine documents were checked against the code. Every one describes a real gap, and none overstates what exists. The markers at Privacy 7.4 and Cookie 5.2 are unusually candid — Privacy 7.4 volunteers that "account closure anonymises the profile rather than deleting it", which is exactly what `convex/users.ts:482–487` does. Documents that describe their own shortcomings accurately are rare and worth preserving.

**Analytics consent is genuinely gated.** `app/_layout.tsx:204–205,210` mounts PostHog only when `analyticsConsent === "granted"`. The v2.1 audit found PostHog firing unconditionally on load; that has been fixed properly, not papered over. What remains missing is the record of consent and the withdrawal route (build items 21, 22), not the gate itself.

**The refund windows in code match the policy.** `convex/refunds.ts:19–20` sets `ORDINARY_WINDOW_DAYS = 60` and `FRAUD_WINDOW_DAYS = 365`, matching Refund 4's 60-day ordinary and 12-month fraud windows.

**Match windows do not inflate campaign totals.** `convex/campaignMatches.ts:226` is explicit — "Does not change campaigns.raised" — so matched amounts are tracked as committed budget rather than displayed as money received. Given that ToS 11.6 makes Dono say publicly when a matching party fails to pay, a design that never books the match as raised is the right one.

## A.10 Suggested order of work

Ordered by exposure per unit of effort, not by build-list priority.

1. **A3** — one string in two files, plus a disclosure line. Removes an unqualified false privacy promise from the live checkout. Do this first because it is the cheapest critical fix in the document.
2. **A1** — remove the community-fund charge path. It unblocks the payment-services perimeter memorandum, which several other clauses and the Financial Crime Policy depend on.
3. **A2** — replace the in-app legal content. Every other publication decision is downstream of this; nothing can be published while users are accepting v0.1 stubs.
4. **A4 + A5 together** — one coherent piece of work on the checkout age control.
5. **A6, A11** — both are small, both remove absolute statements the code currently falsifies.
6. **A12, A14** — student-card deletion and the retention jobs. These are the largest remaining pieces and they gate the Privacy Notice and the Verification Notice together.

# PART C — Product behaviour with no contractual cover

Findings in this category are not gaps in the build. They are things the product does that no v2.2 document describes, which means no clause governs them and no risk assessment has considered them.

**C1 — Society subscriptions are an ungoverned donation product.** *(High)*
Recurring giving has moved from campaigns to societies (`convex/stripe.ts:630` `createSocietySubscription`; `convex/schema.ts:264–303`), and each invoice is **split evenly across the society's currently-active campaigns** (`convex/lib/societySubscriptionSplit.ts:15–28`). No v2.2 document describes this product. The only references anywhere in `terms_v2.2/` are an analytics event name in Cookie 3.2 and ROPA row 6, which describes generic "recurring donations". Three consequences follow. First, a donor subscribing to a society cannot know at setup what their money will fund, since the split depends on which campaigns are active when each invoice lands — which is in tension with ToS 12.1's "conditional contribution **to the stated campaign purpose**". Second, ToS 11.5's rule that "if that Campaign closes or is removed, further charges stop" has no analogue for a society whose campaigns all close; the code handles that case by refunding on the platform's initiative, which is A6. Third, an arrangement that pools a donor's monthly payment and redistributes it across a changing set of projects sits uncomfortably close to ToS 8.4's prohibition on "pooled funds". This needs a contractual home before launch, and probably a decision from the founder about whether the product is what was intended.

**C2 — Society subscriptions use a third fee mechanic.** *(High)*
`convex/stripe.ts:716` sets `application_fee_percent: PLATFORM_FEE_RATE * 100` — a raw 5% with no 20p component and no Stripe-cost residual split. So the platform now has three fee behaviours: the flat 5%+20p envelope for one-off campaign donations, a raw 5% for society subscriptions, and the Stripe-cost-plus-3.5-points model the Terms describe and nothing implements. `TASKS_engineering_questions.md` A3 already asks whether the difference is intentional; it remains unanswered, and ToS 16.1 and Donor 6.1 describe a single fee mechanic.

**C3 — A "Verified" badge exists, in a product that says it has none.** *(Medium-High — a code-contradicts-terms finding, placed here with the other verification-label findings)*
ToS 7.3: "Dono does not use 'Verified' badges." Verification 2.1: "There are no 'Verified Student' or 'Verified Campaign' badges." Verification 7.1 permits only plainly worded, dated, factual statements, each linking to the Notice, and expressly rules out "a single combined or unexplained 'Verified' badge."

The product ships exactly that. `app/campaigns/[id].tsx:524–532` renders a bare green circular tick with `accessibilityLabel="Verified campaign"` whenever `campaign.verifications.length > 0` — no text, no date, no explanation, no link, and it collapses four distinct underlying statuses into one mark. `components/community-card.tsx:27–34` and `app/societies/[id].tsx:245–253` render a badge whose label is the literal string `"Verified"`. (`lib/admin-labels.tsx:78` also uses "Verified", but that is an internal Stripe-status chip in the admin portal and carries no user-facing risk.)

`convex/lib/verificationBadges.ts:3–8` (`VERIFICATION_LABELS`) does define correct, explanatory labels — "Student status checked by Dono", "Stripe onboarding completed", "Society approved", "Institutionally endorsed" — so the backend is aligned with Verification 7.1. The front end overrides them.

**C4 — "Stripe onboarding completed" is built as a public label the Verification Notice says must not be public.** *(Medium)*
Verification 4.2: the Payment Provider's onboarding status "is recorded internally and **not** shown publicly: every live Campaign has completed it, so a public label would convey nothing while wrongly implying the Payment Provider has assessed the Campaign." `convex/lib/verificationBadges.ts:46–55` emits `stripe_onboarding` into the same badge array consumed by the campaign page.

**C5 — "Institutionally endorsed" has no verification process behind it.** *(Medium)*
Verification 6.1 permits the label "**only** where the Recognised Institution has expressly endorsed that specific Campaign", and Verification 3.5 states plainly that "Dono does not carry out 'institution verification'." In code the badge is emitted from a bare boolean, `institutionallyEndorsed` (`convex/lib/verificationBadges.ts:64–71`), with no evidence field, no recording of who endorsed, and no process that could establish the fact. A label that asserts an institutional relationship, set by an internal flag, is precisely the affiliation claim ToS 4.3 exists to prevent.

**C6 — Profile fields collected but not itemised in the Privacy Notice.** *(Low-Medium)*
`convex/schema.ts:16–35` collects `phone`, `avatarUrl`/`avatarStorageId`, `degree` and `yearInCollege`. Privacy 3.1–3.2 itemises name, email, declared date of birth, institution, college and course, but not a phone number or a profile photo. A notice that lists categories field by field — as this one deliberately does — invites the inference that anything unlisted is not collected.

**C7 — Acceptance records exist for guests but carry no wording.** *(Medium, overlaps build item 23)*
`convex/lib/legalAcceptance.ts` writes acceptance rows for guest donors keyed by `guestKey`, which is good. But because the version string points at a stub whose text can be edited freely (A2, build item 24), the record proves that someone clicked, not what they were shown. ToS 2.2 promises the wording is stored.

# PART D — Consistency between the v2.2 documents

The nine numbered documents and the internal policy set were cross-checked against the sixteen decisions in the change log, and against each other on fees, age, refund initiation, anonymity, complaints routing, beneficiary definition, liability and response deadlines.

**The result is clean.** Two minor drafting tensions were found, and no contradictions.

**D1 — ToS 7.3's absolute phrasing sits awkwardly beside Verification 7.1.** *(Cosmetic)*
ToS 7.3 says flatly "Dono does not use 'Verified' badges." Verification 7.1 permits three named status labels, including "Society approved" and "Institutionally endorsed". Read together the intent is obvious and consistent — no *generic* badge, only explained factual statements — but a reader of the ToS alone would conclude that no status labels are shown at all. Suggest aligning ToS 7.3 with Verification 2.1's narrower formulation ("no 'Verified Student' or 'Verified Campaign' badges").

**D2 — Donor 5.4 omits the society case.** *(Cosmetic)*
ToS 11.5 says a Recurring Donation "supports the Campaign **or Society** you selected". Donor 5.4 covers only "If the Campaign closes or is removed, further charges stop." Given C1, the society case is the one that actually exists in the product, so the omission is the more consequential half. Worth fixing at the same time as C1.

**Checks that passed.** Complaints address: `joindono.team@gmail.com` in all ten documents carrying one, no stragglers. Age: identical in ToS 1.8, ToS 11.4, Donor 2.2, Donor 14.1, Verification 4.3, Privacy 14.2, Children's RA, OSA Procedures. Refund initiation: materially identical in ToS 15.4, Refund 1.2, Refund 6.1, Donor 12.1, Student 9.2, Society 4.2. Beneficiary: defined once in ToS 3.1 and applied consistently.

This is a marked improvement on v2.1, where the reconciliation report recorded 92 items. The remaining work is almost entirely between the documents and the code, not between the documents.

# PART E — Questions that need a decision, not a build

These are not engineering tasks. Each needs a founder or counsel decision before the corresponding clause can be finalised.

1. **Is the society subscription product intended?** (C1) If yes, it needs its own contractual treatment and a check against ToS 8.4's pooled-funds prohibition. If it was an interim step, ToS 11.5 and Donor 5.4 should be rewritten around it rather than around the removed campaign-level feature.
2. **Are community funds being removed, or authorised?** (A1) The Terms assume removal. If the intention is to keep them, the clause set, the Financial Crime Policy and the perimeter memorandum all need rebuilding around an authorised model — a much larger piece of work.
3. **What is the under-spend de minimis threshold?** Four documents carry `[TO BE CALCULATED BY DONO TEAM]`; the code uses `0`, which refunds everything. Zero is defensible and honest, but it is not what the clause describes.
4. **Should the A6 carve-out be drafted, or the code changed?** Changing the code preserves the absolute "no reserve power" statement, which is worth more than the safety net it costs.
5. **Does "Institutionally endorsed" survive?** (C5) Verification 3.5 says Dono performs no institution verification. Either build a process that could establish the fact, or remove the label.
6. **Who re-accepts, and when?** (A2) Replacing the in-app legal text means every existing user has accepted a document Dono does not intend to rely on. The re-acceptance plan is a legal decision about the existing user base, not a deployment detail.
